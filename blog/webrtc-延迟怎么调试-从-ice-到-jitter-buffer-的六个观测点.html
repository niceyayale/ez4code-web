WebRTC 延迟怎么调试：从 ICE 到 jitter buffer 的六个观测点

一次 500 人的线上分享里，讲师端一切正常，观众端画面比声音慢约 1.4 秒，评论区刷成一片。事后复盘发现，编码参数、网络带宽、服务器都在正常区间，问题出在接收端的 jitter buffer：丢包率 0.3%，但到达间隔抖动 68 ms，缓冲区被撑到 240 ms 以上，叠加两跳转发后稳定滞后。这个案例说明一件事：WebRTC 延迟不是单一指标，只盯一个数字永远定位不到根因。

一、先把延迟拆成四段

端到端延迟 = 采集编码 + 网络传输 + 抖动缓冲 + 解码渲染。每一段的量级和观测手段都不同，混在一起看只会得出「网络不好」这种无用结论。

| 环节 | 典型值 | 观测手段 | 超标信号 |

|---|---|---|---|

| 采集 + 编码 | 30–80 ms | framesEncoded、totalEncodeTime | 编码队列持续增长 |

| 网络传输 | 20–150 ms | currentRoundTripTime、packetsLost | RTT 抖动 > 50 ms |

| 抖动缓冲 | 20–200 ms | jitterBufferDelay、jitterBufferEmittedCount | 单值 > 200 ms |

| 解码渲染 | 10–50 ms | framesDecoded、freezeCount | 卡顿计数递增 |

二、用 getStats 定点取样

不要用肉眼判断卡顿。WebRTC 的标准统计接口是 RTCPeerConnection.getStats()，W3C 的 WebRTC 1.0 规范（w3c.github.io/webrtc-pc）定义了字段含义，Chromium 与 Firefox 都已实现。取样时按 1 秒一轮、连续 30 轮，才能看出趋势而不是瞬时噪声：

const pc = new RTCPeerConnection(config);
setInterval(async () => {
  const stats = await pc.getStats();
  stats.forEach((r) => {
    if (r.type === 'candidate-pair' && r.state === 'succeeded') {
      console.log('rtt', Math.round(r.currentRoundTripTime * 1000), 'ms');
    }
    if (r.type === 'inbound-rtp' && r.kind === 'video') {
      console.log('jitter', Math.round(r.jitter * 1000), 'ms');
      console.log('lost', r.packetsLost, 'recv', r.packetsReceived);
      console.log('jbDelay', Math.round((r.jitterBufferDelay / r.jitterBufferEmittedCount) * 1000), 'ms');
    }
  });
}, 1000);

三个容易读错的字段

  • jitter 是 RTP 层到达间隔的统计方差，单位秒，RFC 3550 里有精确定义，它不等于延迟。
  • jitterBufferDelay / jitterBufferEmittedCount 才是缓冲带来的真实平均耗时，比 jitter 更接近用户体感。
  • packetsLost 与 packetsReceived 要一起看，前者是累计值，重传成功不会回退。

三、WebRTC 延迟的六个判定阈值

把上面的数据落到判断上，可以先用下面的经验阈值过一遍，超过就往下查：

  1. currentRoundTripTime > 150 ms：先看 ICE 是否走了 TURN 中继，再看物理距离。
  2. 丢包率 > 2%：区分 Wi-Fi 空口丢包与上行拥塞，用 transport 统计里的 bytesSent 增速对照码率。
  3. jitter > 30 ms 且持续 5 秒以上：检查是否跨运营商、是否经过多跳转发。
  4. jitterBufferDelay 均值 > 200 ms：接收端在「用延迟换流畅」，需要下调缓冲上限或改善丢包。
  5. freezeCount 或 pauseCount 递增：解码侧资源不足，检查 CPU 占用与分辨率。
  6. 编码队列 totalEncodeTime 持续高于帧间隔：发送端已过载，应降码率或降分辨率，而不是继续加带宽。

四、网络侧复现与验证

浏览器内的统计只能说明「发生了什么」，要定位「为什么」还得在链路上复现。Linux 下用 tc 注入抖动最直接：

# 在回环网卡上注入 40ms 抖动 + 1% 丢包，模拟移动网络
sudo tc qdisc add dev lo root netem delay 20ms 20ms distribution normal loss 1%
# 验证完记得清理
sudo tc qdisc del dev lo root

抓包侧用 Wireshark 的 RTP 分析（Statistics → RTP → Show all streams）能直接看到序列号缺口与到达时刻，比读统计字段更接近真相。Chrome 自带 chrome://webrtc-internals 会以图表形式记录每一轮的 getStats 结果，用来对比「改动前 / 改动后」很方便。第三方工具里，Twilio Network Test 给出的是端到端网络质量基线，WebRTC Samples 的 peer connection demo 适合验证候选对，Open Relay 的 TURN 服务可以用来对照中继前后的 RTT 差异。

五、常见问题

Q：只测一次 getStats 为什么不够？

单次取样只能看到瞬时值，丢包与抖动都是统计量，1 秒一轮连续 30 轮才能区分偶发与持续劣化。

Q：RTT 正常但画面仍然卡，先查哪里？

查接收端 jitter buffer 与解码耗时。RTT 只覆盖网络往返，不包含缓冲与渲染，这两段加起来经常超过 300 ms。

Q：TURN 中继一定会增加延迟吗？

会增加一跳 RTT 与被中继链路的带宽上限，但如果直连质量差，中继反而更稳定。判断依据是 candidate-pair 的类型与实测 RTT，而不是猜测。

六、处置顺序

按「先确认哪一段超标，再动对应开关」的顺序处理：RTT 超标先查候选对与中继；丢包超标先查无线与拥塞控制；jitter buffer 超标先查抖动来源，再考虑是否允许更激进的自适应；解码卡顿先降分辨率。把六个观测点做成一张每次发布会看的看板，比事后翻日志高效得多。需要浏览器侧的连通性初筛时，可以用 ez4code.com 的 WebRTC 检测页先确认候选对能否建立，再进入上面的逐段排查。
